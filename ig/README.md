# `ig/` — Kenya's FHIR Implementation Guides, vendored

Kenya publishes its own FHIR Implementation Guides. **They are the authority for
terminology, cardinalities and invariants across TaifaHealth** — not the IPS
publication they derive from, not WHO SMART Guidelines, not the ICD-11 roadmap.
Where an international publication and a Kenyan package disagree, the Kenyan
package wins, and the disagreement gets written down here.

This directory holds the packages themselves, a tool that reads conformance
facts out of them, the rules those facts imply, and a harness that runs the
official HL7 validator against them.

| file | what it is |
|---|---|
| [`PINS.md`](PINS.md) | the pin: package name, version, canonical, build date, sha256 of every tarball |
| [`CONFORMANCE_RULES.md`](CONFORMANCE_RULES.md) | the testable rules, each tagged to a StructureDefinition and element, plus upstream defects and our deviations |
| `packages/<ig>/package/` | the extracted package, verbatim |
| `dist/<ig>.tgz` | the tarball the pin's sha256 is of |
| `extract/<ig>-summary.json` | machine-readable conformance facts, regenerated by the tool |
| `tools/extract_ig.py` | reads the packages, emits the summaries |
| `tools/validate.sh` | runs the official HL7 validator with all four packages loaded |
| `tools/fetch.sh` | re-downloads, checks the pins, re-extracts |

```sh
ig/tools/fetch.sh                      # verify pins against upstream
python3 ig/tools/extract_ig.py         # regenerate extract/
ig/tools/validate.sh path/to/bundle.json
```

All four target **FHIR R4 (4.0.1)**. All four are **continuous-integration
builds off feature branches**, not published releases — see `PINS.md` for why
that means the committed tree, not the URL, is the artifact of record.

which IG defines it:

## The bindings that constrain our data model

Read out of `ke.fhir.patient-summary@0.1.0`. Every one of these is **Required**
strength, which in FHIR means a code from the value set is mandatory — not a
suggestion.

| element | ValueSet | resolves to | note |
|---|---|---|---|
| `Condition.code` | `condition-code-vs` | `http://hl7.org/fhir/sid/icd-10` | the whole of ICD-10, unfiltered |
| `MedicationStatement.medication[x]`, `Medication.code` | `kps-medication-vs` | `kps-medication-atc-cs` | Kenya-hosted ATC, **not** `http://www.whocc.no/atc` |
| `AllergyIntolerance.code`, `.reaction.substance` | `allergy-intolerance-code-vs` | `kps-substances-cs` (500) | **not** SNOMED CT |
| `AllergyIntolerance.reaction.manifestation` | `allergy-intolerance-reaction-manifestation-vs` | `manifestation-cs` (30) | **not** SNOMED CT |
| `Immunization.vaccineCode` | `immunization-vaccine-code-vs` | `kps-vaccine-atc-cs` (132) | ATC `J07…`, Kenya-hosted |
| `Immunization.protocolApplied.targetDisease` | `immunization-target-disease-vs` | `kps-target-diseases-cs` | ICD-10 *content*, Kenyan *system* URI |
| `Procedure.code` | `procedure-code-vs` | `kps-procedures-cs` (975) | |
| `DiagnosticReport.code` | `kps-investigations-vs` | `ksp-investigation-cs` (2183) | note the `ksp` typo in the id |
| `Patient.gender` | `kps-patient-gender-vs` | `administrative-gender` | |

Three consequences worth stating plainly:

1. **Diagnoses are ICD-10, bound Required.** ICD-11 has no place in a KPS
   `Condition.code` today.
2. **Medications are ATC, but under a Kenyan `system` URI.** Emitting the WHO
   canonical `http://www.whocc.no/atc` is non-conformant even with identical
   codes.
3. **Immunization `targetDisease` is ICD-10 content under a *different* system
   URI than `Condition.code` uses.** The same disease is coded two ways
   depending on which resource it appears in. That asymmetry is real.

### Patient identity

`Patient.identifier` is 1..*, sliced by system, each slice 0..1:

| slice | system |
|---|---|
| `NationalIDNo` | `http://moh.kenya/identifier/nationalID-no` |
| `UPI` | `http://moh.kenya/identifier/UPI` |
| `PassportNo` | `http://moh.kenya/identifier/passport-No` |
| `BirthCertificateNo` | `http://moh.kenya/identifier/birthCertificate-No` |

Invariant `PatientIdentification-1` (error): at least one of **National ID or
Birth Certificate**. The UPI does not satisfy it. Mind the casing — `-no`
lowercase on the national ID, `-No` capital on the other two. It is
inconsistent and it is compared exactly.

### Notifiable diseases

**There is no notifiable-disease ValueSet in any of the four packages.** Nothing
matching notifiable / surveillance / reportable / IDSR / epidemic / outbreak
exists across all 359 ValueSets and 441 CodeSystems. Reportability flagging is
ours, sourced outside the IGs, and must not be presented as IG-backed.

## Upstream defects

Confirmed against the official validator. Full detail in `CONFORMANCE_RULES.md`.

* **D1 — the KPS CodeSystem canonical base is split.** All 131 KPS CodeSystems
  are published at `…/ig/patient-summary/CodeSystem/…`, but 14 of 39 Kenyan
  ValueSet includes and **all 19 Kenyan codings in the IG's own examples** use
  `https://fhir.dha.go.ke/fhir/CodeSystem/…`, which is published nowhere. Emit
  the published base; do not copy the examples.
* **D2 — `content: complete` code systems are truncated at exactly 1000
  concepts.** `kps-medication-atc-cs` stops at `B02BX01`; `kps-target-diseases-cs`
  stops inside ICD-10 chapter I. Treat as `fragment`, never as grounds to reject
  a code.
* **D3 — the IG's own `DiagnosticReportKPS` example fails validation**, purely
  because of D1.
* **D4 — `http://localhost:8085/…` placeholders persist** in 16 Emergency IG
  ValueSets. Still unfixed on the `removedUnusedProfiles` branch.
* **D5 — 146 of 248 KPS ValueSets are empty** (no compose, no expansion). One,
  `medication-form-vs`, is bound Required from `Medication.form`.
* **D6 — cross-IG canonical drift**: KPS references `kpsg-referral-codes` at a
  DHA URL, but only the Emergency IG publishes it, under an SHA URL.

## Validator verdict on the IG's own content

`ig/tools/validate.sh` with all four packages loaded, FHIR 4.0.1, terminology
server disabled:

* **31 of 32 KPS examples pass.** The one failure is
  `DiagnosticReport-DiagnosticReportKPS.json` (defect D3).
* The **`CompositionKPS` example passes cleanly** — 0 errors, 0 warnings.
* A document Bundle assembled from the IG's own examples
  (`taifa-emr/testdata/kps/ig-example-document-bundle.json`) **passes** with 8
  terminology warnings, every one of them defect D1.
* Our own exporter's bundle (`taifa-emr/testdata/kps/taifa-export.json`, which
  mirrors `taifa-emr/internal/service/kps.go`) **fails** with 16 errors. The
  causes are itemised as F1 to F6 in `taifa-emr/docs/IG_CONFORMANCE.md`,
  "Official validator findings". Three of them (F1 section code displays, F2
  `fullUrl` UUID syntax, F3 the missing `Bundle.identifier`) are ours to fix and
  account for 12 of the 16. Two more (F4 `Observation.category`, F5 the
  allergen and medication codings) are blocked or distorted by upstream defects
  D1a and D2.

The harness is proven against negative controls: removing the Problems section,
stripping the national ID, changing a pattern's `display`, and deleting `meta`
each produce the expected error.

## Working on this

* Do not hand-edit anything under `packages/` or `extract/`. Change the pin,
  re-run `fetch.sh --update`, then `extract_ig.py`, and review the diff.
* `tools/validator_cli.jar` (~190MB) is fetched on demand and is gitignored.
* When our implementation and a package disagree, the package wins and the
  disagreement is recorded under "Deviations found" in `CONFORMANCE_RULES.md`.
